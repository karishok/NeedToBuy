# NeedToBuy — Auth (OTP) design addendum

Дата: 2026-08-20
Статус: одобрено (design), готовится план реализации.
Контекст: аддендум к [[docs/superpowers/specs/2026-08-20-system-architecture-design.md]] —
тот документ уже фиксирует структуру пакетов, модель данных (`otp_codes`,
`sessions`) и поверхность API для Auth (§1, §3, §4). Этот документ закрывает
оставленные там открытыми числовые параметры и добавляет решения, которых
там не было вовсе (TTL сессии), не переопределяя ничего из уже одобренного.

Продуктовый контекст (email+OTP без пароля/SMS, соц.вход в бэклоге) —
[[docs/mvp-decisions.md]].

## Скоуп

Только Auth-слайс: миграции `otp_codes` + `sessions`, пакет
`backend/internal/auth`, три эндпоинта (`POST /api/auth/otp/request`,
`POST /api/auth/otp/verify`, `POST /api/auth/logout`) и session-middleware
в `httpapi`. Онбординг ребёнка, вишлист, каталог, admin — отдельные
подпроекты, будут спроектированы и реализованы отдельно.

## Параметры одноразового кода

- Код — 6 цифр, криптостойкий рандом (`crypto/rand`).
- `otp_codes.code_hash` — SHA-256(code + email + server-side pepper).
  Не bcrypt: код короткоживущий, одноразовый и уже защищён лимитом попыток —
  дорогой хэш не даёт здесь дополнительной защиты, только лишнюю задержку.
- Срок жизни кода — 10 минут от `created_at`.
- Максимум 5 неверных попыток `verify` на один код; после 5-й неудачи код
  считается сгоревшим (`consumed_at` не проставляется, но код больше не
  принимается) — нужно запросить новый через `/request`. Схема
  `otp_codes` из архитектурного документа не содержит счётчика попыток —
  добавляем `attempts int not null default 0` (инкремент на каждый
  неверный `verify`); это расширение схемы, а не противоречие
  архитектурному документу.
- Повторная отправка кода (`POST /api/auth/otp/request`) на тот же email —
  не чаще одного раза в 60 секунд; более частый запрос возвращает `429`
  с тем же JSON error envelope, что описан в архитектурном документе §5.
- Rate-limiting — только по email (ключ — сам email из запроса), без
  привязки к IP. Осознанный YAGNI-вырез для MVP: соло-продукту с низким
  трафиком IP-throttling пока не нужен; добавляется, если появится abuse.

## Сессия родителя

- Реализация cookie — как решено в архитектурном документе: `HttpOnly`,
  `Secure`, `SameSite=Lax`, значение — ID записи в `sessions`.
- TTL — 30 дней со скользящим продлением: `sessions.expires_at`
  пересчитывается на каждый аутентифицированный запрос внутри
  session-middleware (не только в момент логина), так что активный
  пользователь не разлогинивается между визитами.

## Письма с кодом

- Отправка через `net/smtp`, адрес relay берётся из `internal/config`
  (dev — mailcatcher из docker-compose, как уже зафиксировано в
  архитектурном документе).
- Выбор конкретного прод-провайдера — вне скоупа и этого документа, и
  архитектурного: интерфейс отправки писем это допускает без переделок
  кода Auth-слайса.

## Новый vs существующий пользователь

`POST /api/auth/otp/verify` только апсертит запись в `users` (создаёт, если
email новый) и открывает сессию — никакого отдельного флага "новый
пользователь" в ответе нет. После успешного логина фронтенд сам делает
`GET /api/children`: пустой список ⇒ показывает экран онбординга ребёнка,
непустой ⇒ ведёт в вишлист. Контракт `GET /api/children` уже описан в
архитектурном документе §4, изменений не требует.

## Вне скоупа этого документа

- Онбординг ребёнка, вишлист, каталог, admin-модерация — отдельные
  подпроекты с собственными design-аддендумами.
- IP-based throttling, соц.вход (VK ID / Яндекс ID), выбор прод
  email-провайдера — уже отложены согласно
  [[docs/mvp-decisions.md]] и/или архитектурному документу.
