# Каталог: админка модерации — дизайн

Дата: 2026-08-22
Статус: одобрено (design), готовится план реализации.
Контекст: продолжение [[docs/superpowers/specs/2026-08-21-catalog-design.md]] (браузинг
каталога, уже реализован и смержен) и [[docs/superpowers/specs/2026-08-20-system-architecture-design.md]]
(там же изначально заложены `status`/`source` и админ-гейтинг по email).

## Цель

Дать Карине (единственному модератору) возможность руками добавлять,
редактировать и публиковать/скрывать товары общего каталога — без ИИ-генерации
(она осознанно вынесена в отдельный будущий заход, выбор ИИ-вендора не
блокирует этот).

## Что меняется в уже реализованном каталоге

Публичный каталог уже в проде (в деве) в форме «1 товар = 1 возраст +
1 категория». В процессе этого захода выяснилось, что один и тот же товар
может подходить нескольким возрастам и категориям одновременно (например,
книжка-непромокашка — и 12 мес., и 18 мес., категории «книги» и «игрушки»
сразу) — модель данных меняется на мультивыбор, это не только новая
админ-функциональность, но и доработка существующей схемы/API/фронтенда
каталога.

## 1. Схема данных

`catalog_items` теряет колонки `age_range_code`/`category` (переезжают в
таблицы связей ниже) и получает:
```sql
ALTER TABLE catalog_items ADD COLUMN status TEXT NOT NULL DEFAULT 'published';
```
`status` — `published`/`hidden`, проверяется в Go-коде (не через DB CHECK),
как и `category` раньше. `source`/`approved_at` из архитектурного документа
**не добавляются** — они нужны только для ИИ-воркфлоу, которого в этом
заходе нет; добавятся отдельной миграцией, когда появится ИИ-генерация.

Новые таблицы связей (классический many-to-many, составной PK):
```sql
CREATE TABLE catalog_item_age_ranges (
    catalog_item_id BIGINT NOT NULL REFERENCES catalog_items(id) ON DELETE CASCADE,
    age_range_code TEXT NOT NULL,
    PRIMARY KEY (catalog_item_id, age_range_code)
);

CREATE TABLE catalog_item_categories (
    catalog_item_id BIGINT NOT NULL REFERENCES catalog_items(id) ON DELETE CASCADE,
    category TEXT NOT NULL,
    PRIMARY KEY (catalog_item_id, category)
);
```
`age_range_code`/`category` в этих таблицах — не FK на отдельную справочную
таблицу: валидация происходит в Go через уже существующие
`agerange.IsValid`/`catalog.IsValidCategory`, те же 23 кода и 4 категории,
никакой новой справочной таблицы не заводится.

Выбор в пользу таблиц связей, а не Postgres-массивов (`TEXT[]`) —
осознанное решение: массивы потребовали бы `pq.Array` для sqlx-сканирования
(новая зависимость сверх уже используемого набора) и не дают такой же
относительной строгости (уникальность элементов внутри массива — только на
совести приложения). Таблицы связей ложатся на уже используемый в проекте
паттерн плоских реляционных таблиц без ORM.

**Миграция существующих данных:** одна миграция делает всё разом — добавляет
`status`, создаёт обе новые таблицы, копирует текущие пары
`(age_range_code, category)` из уже засеянных 18 товаров в новые таблицы,
удаляет старые колонки из `catalog_items`. Все существующие товары получают
`status='published'` (они уже видны публично — остаются видны).

## 2. API

**Публичный `GET /api/catalog?age_range=&category=`** — адрес и публичность
не меняются, меняется форма ответа:
```json
{
  "id": 1,
  "title": "...",
  "marketplace_search_url": "...",
  "image_url": null,
  "age_range_codes": ["12m", "18m"],
  "categories": ["books", "toys"]
}
```
Возвращаются только `status='published'` товары; `status` наружу не
отдаётся — внутренняя деталь. Товар входит в выборку, если фильтр по
возрасту пуст ИЛИ значение есть среди `age_range_codes`, и аналогично для
категории. Оба условия (`published` + оба фильтра) объединяются через `AND`.

**Админские эндпоинты** (`/api/admin/catalog`, все требуют сессию + гейт
админа — см. ниже):
- `GET /api/admin/catalog` — полный список (и `published`, и `hidden`), та
  же форма ответа + поле `status`.
- `POST /api/admin/catalog` — создать:
  ```json
  {"title": "...", "marketplace_search_url": "...", "image_url": null,
   "age_range_codes": ["12m", "18m"], "categories": ["books", "toys"],
   "status": "published"}
  ```
  201 + созданный товар в той же форме.
- `PATCH /api/admin/catalog/{id}` — частичное редактирование: любое из полей
  выше; если поле присутствует в теле запроса — оно заменяет текущее
  значение целиком (для `age_range_codes`/`categories` — полная замена
  набора тегов, не мердж); отсутствующее поле не трогается. 200 + обновлённый
  товар.
- Удаления нет — только тоггл `published`/`hidden` через `PATCH`.

**Гейтинг:** новый `auth.RequireAdmin` — мидлварь-метод на `auth.Handler`
(нужен доступ к БД для email по user id, поэтому не может быть свободной
функцией, как `RequireAuth`), регистрируется после `auth.RequireAuth` на
всех `/api/admin/*` роутах. Сверяет email вошедшего с `config.AdminEmail`
(по умолчанию `babaliants@gmail.com`, переопределяется переменной окружения
`ADMIN_EMAIL`). Без сессии → 401 (ловит `RequireAuth`), с сессией
не-админа → 403.

`GET /api/auth/me` дополняется полем `is_admin: bool` (сравнение email с
`config.AdminEmail` там же, где считается ответ).

## 3. Фронтенд

**Правки существующего публичного каталога:**
- `CatalogItem` в `client.ts`: `age_range_code`/`category` →
  `age_range_codes: string[]`/`categories: string[]`.
- Карточка в `CatalogPage` рендерит несколько тегов возраста и несколько
  тегов категории вместо одного. Сами фильтры остаются одиночным выбором
  (один возраст + одна категория за раз) — меняется только то, как
  проверяется совпадение на бэкенде.

**Новый роут `/admin`:**
- `Session`/`AuthContext` получают поле `is_admin` вслед за бэкендом. Ссылка
  «Админка» в `AppNav` видна только при `session.is_admin === true`.
- Новый фронтовый guard-компонент `RequireAdmin` (по аналогии с уже
  существующим `RequireAuth`) — не-админа или анонима, зашедшего на `/admin`
  напрямую по URL, редиректит на `/`.
- Страница админки: список всех товаров (`published` и `hidden`) с тегами и
  статусом; кнопка «Добавить товар»; клик по товару открывает форму
  редактирования с уже заполненными полями. Без удаления — только чекбокс
  «опубликован» в форме.
- Форма (общая для создания и редактирования): заголовок, ссылка на Ozon,
  ссылка на фото (необязательно), чекбоксы возрастов — сгруппированы так же,
  как в фильтре каталога, по тем же 5 периодам (`AGE_GROUPS`/`AGE_LABELS`),
  чекбоксы категорий (все 4 галочками), чекбокс «опубликован» (по умолчанию
  включён для нового товара).
- Новый компонент `CheckboxGroup` (список чекбоксов с общим лейблом) —
  используется дважды: для возрастов (по группам) и категорий (плоский
  список из 4).
- Новые функции клиента: `getAdminCatalog()`, `createCatalogItem(...)`,
  `updateCatalogItem(id, ...)`.

## 4. Обработка ошибок и тестирование

**Валидация (create/update):**
- `age_range_codes`/`categories` — непустые массивы (иначе товар физически
  никогда не появится в каталоге), каждый код проверяется через
  `agerange.IsValid`/`IsValidCategory` → 400 на первое же плохое значение.
- `title`/`marketplace_search_url` — обязательные непустые строки → 400.
- `status` — только `published`/`hidden` → 400 на любое другое значение.
- Гейтинг: без сессии → 401, сессия не-админа → 403, `PATCH` на
  несуществующий `id` → 404.

**Тестирование:**
- Backend: repository-тесты на фильтрацию по множественным тегам (товар с
  2 возрастами/2 категориями находится по любому из них, а не только по
  первому), хендлер-тесты на `create`/`list`/`update` и все
  400/401/403/404-случаи, e2e-тест в `httpapi`, явно проверяющий, что
  `/api/admin/catalog` отвечает 401 без сессии и 403 сессии не-админа — по
  аналогии с уже существующим e2e-тестом на публичность `/api/catalog`.
- Frontend: обновление тестов `CatalogPage` под множественные теги, новые
  тесты `AdminPage` (список, создание, редактирование, тоггл публикации),
  тест на то, что «Админка» в навигации видна только `is_admin`, и что
  прямой заход на `/admin` не-админом уводит на `/`.

## Вне скоупа этого документа

- ИИ-генерация предложений (`catalog.Suggester`, выбор вендора) — отдельный
  будущий заход.
- Полное удаление товара — только `published`/`hidden`.
- Загрузка фото файлом — только текстовое поле-ссылка, как и раньше.
- Таблица ролей — единственный админ определяется одним email в конфиге.
- Пагинация в админском списке — датасет пока маленький (растёт вручную,
  по одному товару за раз).
