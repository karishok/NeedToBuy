# NeedToBuy — Child Profile (backend) design

Дата: 2026-08-21
Статус: одобрено (design), готовится план реализации.
Контекст: третий бэкенд-срез после [[docs/superpowers/specs/2026-08-20-auth-otp-design.md]].
Продолжает [[docs/superpowers/specs/2026-08-20-system-architecture-design.md]] (модель
`children` и API-поверхность там уже намечены в общих чертах) и
[[docs/mvp-decisions.md]] (возрастная сетка, требование согласия по 152-ФЗ,
роль родителя).

Только бэкенд, как и `[[docs/superpowers/specs/2026-08-20-auth-otp-design.md]]`
для Auth — фронтенд-онбординг делается отдельным срезом позже, вместе с
экраном вишлиста (submit онбординга в продукте ведёт прямо в вишлист, так
что делать один без другого бессмысленно).

## Скоуп

**В этот срез:**
- Пакет `backend/internal/child` — полный CRUD профилей ребёнка
  (`POST/GET/PATCH/DELETE /api/children[/{id}]`).
- Миграция таблицы `children`.
- Пакет `backend/internal/agerange` — расчёт возрастной группы по дате
  рождения, без БД-таблицы (зафиксировано в mvp-decisions).
- Множественные дети на одного родителя — поддержаны сразу, не
  искусственно ограничено одним.

**Вне скоупа:**
- Фронтенд (онбординг-экран, отображение в шапке вишлиста).
- `wishlist_items` — таблица и её FK на `children` появятся в будущей
  миграции wishlist-среза.
- Публичный gifter-эндпоинт (`GET /api/public/wishlist/{token}`) — использует
  `public_share_token`, которое этот срез генерирует и хранит, но сам
  эндпоинт — часть будущего wishlist-среза.
- Человекочитаемое форматирование возраста («2 года», русские склонения
  «1 месяц»/«2 месяца»/«5 месяцев») — фронтенд-забота; бэкенд отдаёт
  только машиночитаемый код возрастной группы.

## 1. Модель данных

Расширяет модель из архитектурного документа одним полем — `updated_at`,
нужным для `PATCH` (аналогично тому, как `attempts` добавился к
`otp_codes` в Auth-срезе — не противоречие исходной архитектуре, а
уточнение при реализации).

```sql
CREATE TABLE children (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    parent_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    birth_date DATE NOT NULL,
    public_share_token TEXT NOT NULL UNIQUE,
    consent_child_data_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX children_parent_id_idx ON children (parent_id);
```

Миграция: `000004_create_children` (следующий свободный номер после
`000003_create_sessions`).

`public_share_token` — случайный непредсказуемый токен, та же схема, что
у `sessions.id` в Auth-срезе (`crypto/rand`, hex-encoded), генерируется
один раз при создании профиля. `consent_child_data_at` не `NULL`able:
раз API требует `consent=true` при создании (см. §2), запись без
согласия физически не может появиться в таблице.

## 2. API-поверхность и валидация

Все маршруты — за уже существующими `authHandler.Middleware` +
`auth.RequireAuth`; владелец определяется через `auth.UserID(ctx)`.

```
POST   /api/children        {name, birth_date, consent}  → 201 {child}
GET    /api/children                                      → 200 [child, ...]
PATCH  /api/children/{id}   {name?, birth_date?}          → 200 {child}
DELETE /api/children/{id}                                  → 200 {"status":"ok"}
```

Отдельного `GET /api/children/{id}` нет — сейчас его нечем наполнить
(список закрывает текущую потребность), добавится вместе с первым
реальным потребителем (например, экраном вишлиста). `PATCH` не
принимает `consent` — согласие фиксируется один раз при создании и не
отзывается через API в MVP (единственный способ убрать данные —
`DELETE` всего профиля).

Тело ответа `{child}`:

```json
{
  "id": 1,
  "name": "Тимофей",
  "birth_date": "2024-03-15",
  "age_range_code": "18m",
  "public_share_token": "…",
  "created_at": "…",
  "updated_at": "…"
}
```

`age_range_code` пересчитывается на лету при каждом ответе из
`birth_date` (см. §3) — не хранится в БД, не протухает при смене даты
рождения через `PATCH`.

**Валидация:**
- `name` — обязательное, `strings.TrimSpace`, непустое после trim,
  максимум 100 символов.
- `birth_date` — обязательная валидная дата, не в будущем относительно
  `time.Now()`. Верхней границы в прошлом нет — группа `12y+` покрывает
  любой более старший возраст без спецслучаев.
- `consent` — на `POST` обязательно `true`, иначе `400 bad_request`
  через стандартный `apierr`-конверт. На `PATCH` не участвует.

**Владение:** `GET` отдаёт только детей текущего родителя (`WHERE
parent_id = $1`). `PATCH`/`DELETE` чужого или несуществующего `id` →
`404 not_found` — не `403`, чтобы не подтверждать чужому пользователю
сам факт существования записи (та же конвенция, что уже используется в
`apierr.NotFound`).

## 3. Возрастная сетка (`internal/agerange`)

Отдельный пакет, только Go-константы — без таблицы в БД и без
админ-панели для редактирования сетки (зафиксировано в
`docs/mvp-decisions.md`).

```go
// CodeFor returns the age-bucket code for a child born on birthDate, as
// of asOf — the lower bound of the bucket the child currently falls
// into (the upper bound is implicitly "up to the next bucket's code").
func CodeFor(birthDate, asOf time.Time) string
```

23 бакета, код — нижняя граница интервала + суффикс единицы (`m`/`y`);
суффикс обязателен, потому что месяцы и годы пересекаются по числу
(например, `3m` ≠ `3y`):

```
0m 1m 2m 3m 4m 5m                     — 0–6 мес, помесячно
6m 9m 12m 15m                          — 6–18 мес, по 3 мес
18m 24m 30m                            — 18 мес–3 года, по полгода
3y 4y 5y 6y 7y 8y 9y 10y 11y           — 3–12 лет, погодично
12y+                                    — 12+, без верхней границы
                                          (нет «следующего кода», поэтому
                                          суффикс «+» — явный сигнал, что
                                          отсюда границы не подразумеваются)
```

Пример: ребёнку 20 месяцев на момент запроса → `"18m"` (последняя
граница ≤ 20 мес до следующей, `"24m"`).

## 4. Обработка ошибок и тестирование

Ошибки — тот же JSON-конверт `apierr`, что и везде: `apierr.BadRequest`
для валидации (пустое имя, дата в будущем, `consent≠true`),
`apierr.NotFound("child")` для чужого/несуществующего `id`,
`apierr.Internal` для сбоев БД.

Тесты — паттерн пакета `auth`: `httptest` + `dbtest.Tx`, репозиторные
функции принимают `auth.Querier` напрямую (он уже экспортирован именно
для переиспользования другими пакетами — заводить дублирующий интерфейс
в `internal/child` было бы лишней сущностью). Обязательные кейсы:
- создание без согласия → `400`;
- создание с датой рождения в будущем → `400`;
- `GET`/`PATCH`/`DELETE` изолируют родителей друг от друга (родитель A не
  видит и не может тронуть ребёнка родителя B) → `404` для чужого `id`;
- `agerange.CodeFor` — табличный тест на границы бакетов (кто ещё на
  прошлой границе, кто уже перешёл на следующую, включая переход
  30m → 3y и последний переход в `12y+`).

## Вне скоупа этого документа

- Фронтенд-онбординг и отображение ребёнка в шапке вишлиста — отдельный
  срез, делается вместе с экраном вишлиста.
- `wishlist_items`, публичный gifter-эндпоинт, каталог — отдельные
  будущие срезы, зависящие от этой модели данных (`children.id`,
  `public_share_token`).
- Русская грамматика для отображения возраста — фронтенд-забота.
