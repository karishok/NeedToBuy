# NeedToBuy — Catalog browsing screen design

Дата: 2026-08-21
Статус: одобрено (design), готовится план реализации.
Контекст: продолжает [[docs/superpowers/specs/2026-08-20-system-architecture-design.md]]
(модель `catalog_items` и API-поверхность там намечены в общих чертах) и
[[docs/mvp-decisions.md]] (каталог — текстовые идеи со ссылкой на поиск
Ozon, ИИ-подбор + модерация как будущий отдельный механизм). Опирается на
уже реализованные [[docs/superpowers/specs/2026-08-20-auth-otp-design.md]],
[[docs/superpowers/specs/2026-08-21-frontend-foundation-auth-design.md]] и
[[docs/superpowers/specs/2026-08-21-child-profile-design.md]] (переиспользует
`internal/agerange`'s 23 кода возрастных бакетов напрямую).

В отличие от Auth и Child Profile (бэкенд отдельным срезом, фронтенд —
отдельным), здесь бэкенд-часть маленькая (только просмотр, без
admin/AI), поэтому бэкенд и фронтенд делаются одним срезом — по образцу
[[docs/superpowers/specs/2026-08-21-frontend-foundation-auth-design.md]].

## Скоуп

**В этот срез:**
- Таблица `catalog_items` + сид тестовых данных.
- `GET /api/catalog?age_range=&category=` — просмотр с фильтрами.
- Фронтенд-экран каталога, заменяющий `PlaceholderHome` как главный экран
  после логина (`/`).
- Маленький общий `AppNav` (бренд + логаут) — раньше логаут жил только в
  `PlaceholderHome`, теперь ему нужен постоянный дом, раз каталог —
  полноценный экран, а не заглушка.

**Вне скоупа:**
- Admin-панель модерации, ИИ-генерация каталожных предложений.
- Кнопка «Добавить в вишлист» — вишлиста ещё нет; экран этого среза —
  чистый браузинг + переход на Ozon.
- Пагинация — сид-датасет маленький.
- Персонализация фильтра под конкретного ребёнка — онбординг ребёнка
  на фронтенде ещё не реализован (только бэкенд из
  [[docs/superpowers/specs/2026-08-21-child-profile-design.md]]), так что
  у родителя сейчас может не быть ни одного профиля. Экран не завязан на
  существование ребёнка; фильтры по умолчанию — «все возраста», «все
  категории».

## 1. Модель данных

Сознательно **без** `status`/`source`/`approved_at` из архитектурного
документа — эти поля существуют только под будущий admin/AI-workflow,
которого в этом срезе нет. Добавятся через `ALTER TABLE` в отдельной
будущей миграции вместе с самой админкой — по той же логике, по которой
`otp_codes.attempts` появился в Auth-срезе по мере необходимости, а не
заранее.

```sql
CREATE TABLE catalog_items (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    age_range_code TEXT NOT NULL,
    category TEXT NOT NULL,
    title TEXT NOT NULL,
    marketplace_search_url TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX catalog_items_filter_idx ON catalog_items (age_range_code, category);
```

`age_range_code` — не FK, использует ровно те же 23 кода, что уже
считает `internal/agerange` (`0m`…`12y+`, см.
[[docs/superpowers/specs/2026-08-21-child-profile-design.md]]) — отдельной
сетки для каталога не заводится. `category` — захардкоженный enum в Go
(`clothes`/`toys`/`books`/`sport`), без БД-таблицы, по той же логике, что
и возрастная сетка (зафиксировано в mvp-decisions: без БД-таблицы и без
админки для её редактирования — здесь применяем тот же принцип к
категориям, раз это тоже маленький фиксированный список).

Сид — ~15–20 текстовых идей (заголовок + ссылка на поиск Ozon),
покрывающих разные возраста и все 4 категории, чтобы экран было что
показать и на чём проверить фильтры.

## 2. API-поверхность

```
GET /api/catalog?age_range=<код>&category=<clothes|toys|books|sport>
```

За `auth.RequireAuth` (как `/api/children`), но не привязан к конкретному
ребёнку — общий каталог, доступный любому залогиненному родителю.

Оба параметра опциональны — отсутствие означает «без фильтра по этому
полю». Ответ — плоский JSON-массив, без пагинации:

```json
[
  {
    "id": 1,
    "age_range_code": "18m",
    "category": "toys",
    "title": "Сортер с крупными деталями",
    "marketplace_search_url": "https://www.ozon.ru/search/?text=..."
  }
]
```

Валидация: переданный `age_range`, не входящий в 23 известных кода
`agerange`, → `400 bad_request`; переданный `category`, не входящий в 4
значения, → `400`. Невалидные значения не игнорируются молча — иначе
опечатка в фильтре на фронтенде тихо покажет пустой список вместо
явной ошибки.

## 3. Фронтенд: экран и навигация

```
frontend/src/
├── components/
│   ├── AppNav.tsx           — бренд + логаут, обёртка над .nav (Organic)
│   ├── Select.tsx           — обёртка над <select class="input">
│   └── Segmented.tsx        — обёртка над .seg/.seg-opt (радио-группа категорий)
└── catalog/
    ├── ageGroups.ts         — фронт-only: 23 кода agerange, сгруппированные в 5
    │                           именованных периодов (только для <optgroup> в
    │                           дропдауне; бэкенд про эту группировку не знает —
    │                           чистая презентационная деталь)
    ├── CatalogPage.tsx       — сам экран: фильтры + сетка карточек
    └── CatalogPage.test.tsx
```

`PlaceholderHome.tsx` удаляется целиком — каталог занимает маршрут `/`
вместо него. `App.tsx` оборачивает защищённый маршрут в `AppNav` +
`CatalogPage`.

`api/client.ts` получает `getCatalog({ageRange?, category?}):
Promise<CatalogItem[]>`. Фильтры по умолчанию — возраст «Все» (без
фильтра), категория «Все»; экран самостоятелен и не требует
существования ребёнка.

Карточка — тег возрастной группы, тег категории, заголовок, кнопка-ссылка
«Открыть на Ozon» (`target="_blank"`). Без отдельного поля
описания/`blurb` — ни в архитектурном документе, ни в mvp-decisions у
каталожной позиции нет ничего, кроме заголовка и ссылки; новое поле ради
вида карточки не заводится.

## 4. Обработка ошибок и тестирование

Ошибки — тот же паттерн, что на `LoginPage`: `ApiError.message` инлайново
под фильтрами, общий фолбэк для сетевых сбоев. Пустой результат
фильтрации — отдельное состояние «ничего не найдено», не ошибка (как в
макете: «Пока нет идей для этого возраста и категории»).

**Бэкенд** — паттерн `internal/child`: `httptest` + `dbtest.Tx`, тесты на
валидацию `age_range`/`category` (400 на неизвестное значение),
комбинации фильтров, миграцию + сид (таблица создаётся, сид виден).
E2e-тест через реальный роутер.

**Фронтенд** — паттерн `LoginPage.test.tsx`: рендер списка, смена фильтра
дёргает `getCatalog` с правильными параметрами, пустой результат
показывает нужный текст, ошибка API показывает сообщение.

## Вне скоупа этого документа

- Admin-модерация, ИИ-генерация каталожных предложений — отдельный
  будущий срез, добавит `status`/`source`/`approved_at` через
  `ALTER TABLE`.
- Вишлист и «Добавить из каталога» — зависит от ещё не спроектированного
  wishlist-среза.
- Персонализация под конкретного ребёнка (дефолт фильтра по его возрасту)
  — когда появится фронтенд-онбординг ребёнка.
