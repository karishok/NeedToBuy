# NeedToBuy — Frontend Foundation + OTP Login design

Дата: 2026-08-21
Статус: одобрено (design), готовится план реализации.
Контекст: первый фронтенд-подпроект. Продолжает
[[docs/superpowers/specs/2026-08-20-system-architecture-design.md]] (стек:
React + TypeScript, SPA, Vite, монорепо) и опирается на уже реализованный
и смёрженный (после ревью) бэкенд-срез
[[docs/superpowers/specs/2026-08-20-auth-otp-design.md]] — `POST
/api/auth/otp/request`, `POST /api/auth/otp/verify`, `POST
/api/auth/logout`.

Макеты — экспорт дизайн-системы «Organic» (`styles.css` + `Wishlist.dc.html`)
из `Scope clarification needed.zip`, покрывающий 6 экранов продукта. Этот
документ реализует только два из них (вход по email/коду) — остальные
(онбординг ребёнка, вишлист, каталог, админка) заблокированы отсутствующими
бэкенд-эндпоинтами и станут отдельными подпроектами.

## Скоуп

**В этот срез входит:**
- Каркас SPA: `frontend/` (Vite + React + TypeScript), роутинг, дизайн-токены
  Organic, тонкий API-клиент.
- Экран входа (email → код), полностью подключённый к реальному бэкенду.
- Восстановление сессии при перезагрузке страницы — требует нового
  бэкенд-эндпоинта `GET /api/auth/me` (единственное изменение бэкенда в
  этом срезе, см. ниже).
- Временная защищённая заглушка после логина («Вы вошли как {email}» +
  кнопка выхода) — не из макета, нужна только чтобы протестировать цепочку
  логин → защищённый маршрут → логаут целиком; её заменит настоящий экран
  вишлиста в отдельном срезе.

**Вне скоупа:** онбординг ребёнка, вишлист, каталог идей, админка
модерации — экраны есть в макете, но нет бэкенда (`child`, `wishlist`,
`catalog` пакеты ещё не спроектированы).

## 1. Бэкенд-дополнение: `GET /api/auth/me`

Единственное изменение вне `frontend/`. Без него фронтенд не может
отличить «сессия жива» от «сессии никогда не было» после F5 — cookie
`HttpOnly`, JS её не видит, а других защищённых эндпоинтов в проде сейчас
нет вовсе.

- `GET /api/auth/me` — если `Middleware` нашло валидную сессию (проверяется
  через уже существующий `auth.RequireAuth`), возвращает `200
  {"email": "..."}`; иначе `401` через тот же `apierr`-конверт, что и везде.
- Требуется маленький репозиторный геттер `emailByUserID(ctx, db,
  userID) (string, error)` рядом с `upsertUser` в `internal/auth/user.go`,
  плюс сам HTTP-хендлер (`Handler.Me`) и регистрация маршрута в
  `router.go` за `authHandler.Middleware` + `auth.RequireAuth`.
- Это первый защищённый маршрут в проде вообще (раньше `RequireAuth`
  использовался только в тестах) — само по себе полезно, закрывает часть
  пробела, отмеченного финальным ревью Auth-PR (там e2e-тест не проверял
  реальный защищённый маршрут).

## 2. Структура `frontend/`

```
frontend/
├── index.html
├── package.json            — Vite + React + TypeScript, без лишних зависимостей
├── vite.config.ts          — dev-прокси /api/* → backend (localhost:8080)
├── tsconfig.json
└── src/
    ├── main.tsx
    ├── App.tsx              — роуты (react-router-dom): /login, / (заглушка)
    ├── styles/
    │   └── organic.css      — styles.css из макета, скопирован без изменений
    ├── api/
    │   └── client.ts        — тонкая обёртка над fetch: credentials:'include',
    │                            парсинг {"error":{code,message}} конверта в
    │                            типизированную ошибку, JSON-сериализация тела
    ├── auth/
    │   ├── AuthContext.tsx   — состояние сессии: 'loading' | {email} | null;
    │   │                        на монтировании дёргает GET /api/auth/me
    │   ├── useAuth.ts        — хук поверх контекста
    │   ├── LoginPage.tsx     — email-стадия и code-стадия одной страницы,
    │   │                        как в макете (login.isEmailStage/isCodeStage)
    │   ├── RequireAuth.tsx   — route-guard компонent: не залогинен → /login
    │   └── PlaceholderHome.tsx — врЕменная защищённая страница
    └── components/           — Button, Card, Field, Tag: обёртки над
                                  классами Organic (.btn/.card/.field/.tag),
                                  без переизобретения разметки из макета
```

Роутинг — `react-router-dom`, стандартный выбор для Vite+React SPA, без
альтернатив под рассмотрение. API-клиент — свой тонкий враппер без
TanStack Query/SWR: на 4 эндпоинта (request/verify/logout/me) кэширование и
дедупликация не нужны — YAGNI.

## 3. Поток входа

Экран `/login` — одна страница с двумя стадиями (state, не отдельные
роуты), 1:1 с макетом:

1. **Email-стадия**: поле email, кнопка «Получить код» →
   `POST /api/auth/otp/request`. Успех → переход в code-стадию. `429`
   (cooldown) → инлайн-сообщение с текстом ошибки от сервера, кнопка
   остаётся активной (сервер уже enforces cooldown, фронт не дублирует
   таймер в этом срезе — YAGNI, можно добавить визуальный countdown позже).
2. **Code-стадия**: поле кода, кнопка «Подтвердить» →
   `POST /api/auth/otp/verify`. Успех → `AuthContext` обновляет состояние
   (email из формы), редирект на `/`. `400` (неверный/просроченный код) →
   инлайн-сообщение под полем, поле кода очищается. Кнопка «Изменить
   почту» возвращает в email-стадию (как в макете).

`AuthContext` при монтировании приложения дёргает `GET /api/auth/me`:
`200` → сессия восстановлена, `401` → не залогинен, сетевая ошибка →
трактуется как «не залогинен» (не блокирует рендер приложения).

`RequireAuth`-guard (React-компонент, не путать с одноимённым Go-хелпером
в бэкенде) редиректит `/` → `/login` для незалогиненных и `/login` → `/`
для уже залогиненных — симметрично серверному `auth.RequireAuth`.

## 4. Обработка ошибок

В макете нет состояний ошибок вовсе (только happy path) — этот раздел
проектируется с нуля. Единый паттерн: инлайн-текст под полем формы для
`400`/`429` (сообщение — из `error.message` ответа сервера, он уже
человекочитаемый на русском по конвенции `apierr`), общее сообщение
«Что-то пошло не так, попробуйте ещё раз» для сетевых ошибок и `5xx`.

У Organic нет отдельного «error»-токена в палитре (только `--color-accent`
и `--color-accent-2`, обе тёплые, не тревожные). Для текста ошибки
используется `--color-accent-700` — тёмный шаг акцентной рампы, уже
предназначенный в дизайн-системе для параграфного текста на акценте
(readme: «for paragraph-size text in the accent use a deep ramp step»).
Не вводим отдельный красный — сохраняет целостность палитры.

## 5. Тестирование

Vitest + React Testing Library (зафиксировано в архитектурном документе).

- `api/client.ts` — юнит-тесты с замоканным `fetch`: успешный запрос,
  парсинг error-конверта, сетевая ошибка.
- `AuthContext` — тест на оба исхода `GET /api/auth/me` (200/401/сетевая
  ошибка) и корректное состояние после успешного `verify`.
- `LoginPage` — интеграционный сценарий целиком: ввод email → код
  запрошен → ввод кода → успешный вход, плюс по одному тесту на `429` и
  `400`.

Бэкенд-часть (`GET /api/auth/me`) тестируется тем же паттерном, что и
остальной `auth` package — `httptest` + `dbtest.Tx`, как в
[[docs/superpowers/specs/2026-08-20-auth-otp-design.md]].

## Вне скоупа этого документа

- Онбординг ребёнка, вишлист, каталог, admin — отдельные подпроекты со
  своими design-аддендумами, зависят от соответствующих бэкенд-срезов.
- Визуальный countdown для resend-кулдауна (сервер уже это enforces).
- Соц.вход (VK ID / Яндекс ID) — отложено согласно
  [[docs/mvp-decisions.md]].
